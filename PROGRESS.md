### What Step 16 inherits from Step 15, in one paragraph

Step 15 left every event NFR-OBS-1 names logged at `notice` or `error`, through `Logger`, on one
subsystem — `com.arc3solutions.USBDriveTester` — in seven categories, the six its step 2 names and
`quit`, with every interpolation `.public` and no device bytes (`progress/step-15-event-audit.md`).
**Every run has one ID**: `RunController` makes a `UUID` when the run is authorised and hands it
through `acquireDevice(bsdName:runID:reply:)`, protocol v16, and both processes head their run lines
with `TesterProtocol.runTag` — `[run <UUID>] ` — so one grep reconstructs a run across the app and
the helper; the app's first tagged line is `run authorised`. The helper's digest line, which only a
gate tool asks for, ends `(N B) taken`, with no hex. **Two platform facts bind any gate that reads
the log**: the store keeps this subsystem's lines only about one to three days on macOS 27.0.1
(NFR-OBS-2's note), so log evidence is exported the day it is made, and a live `log stream` capture
is what survives if it is not; and `log stream` stamps a line 5–20 ms later than `log show`
(`CONSTRAINTS.md` §1), so both ends of a measured gap come from the same tool. Step 16's detailed
step 6 asks for a sane release logging level; the audit is the inventory to read it against. **A
Step 16 install lapses Step 15's gate by its own clause** — another install — and so does an edit to
a `Logger` call on a run's path or a move of the helper source hash; the gate was read on a traced
full run and an interrupted one, the same day (`progress/step-15.md`, *Chunk 5*).
